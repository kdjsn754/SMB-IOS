# 缩略图实现详解
## —— 如何做到「按顺序一个一个加载」与「竖屏横屏按比例显示」

> 对应代码版本：SMBViewer **1.2.0**
> 涉及文件：`Sources/Services/ThumbnailStore.swift`、`Sources/Services/AsyncLimiter.swift`、
> `Sources/Services/ImageDownsampler.swift`、`Sources/Views/Components/MediaTiles.swift`、`Sources/Views/BrowserView.swift`
>
> 本文只讲**当前生效的实现**，以及每个参数为什么是这个值、踩过哪些坑。
> 想看「踩坑全景/跨平台对照」，另见 `docs/开发建议-远端媒体与缩略图踩坑复盘.md`。

---

## 0. 一句话总结

两件事，两套独立机制，不要混在一起：

| 目标 | 机制 | 位置 |
| --- | --- | --- |
| **顺序**：缩略图从左上到右下、一个一个出现 | 给每个格子一个「显示序号 `order`」，所有取图请求过同**一道**有序闸门，闸门一次只放行一个，且总挑序号最小的 | `ThumbnailStore.displayLimiter` = `OrderedLimiter(limit: 1, settle: 250ms)` |
| **比例**：竖屏横屏都不变形、不被裁、格子大小还一致 | **固定展示框**（宽:高 = 1:1.15）+ 图片 `scaledToFit()` + 框内居中，空白处露出页面底色 | `TileAspect.box = 0.87` + `ThumbnailImage` |

关键认知：
**「顺序」不是靠「串行下载」实现的**，串行下载只会慢。真正需要串行的是**「从网络取一张图」这一小段**（瓶颈在 NAS 和小带宽），
而解码、缓存、落地都可以并行走。所以闸门的粒度是「一次一个网络取图」，不是「一次一个任务」。

---

## 1. 全局数据流

```
BrowserView（目录页）
  │  ForEach(Array(visibleItems.enumerated())) → index 就是 order
  ▼
MediaTile(order:)                       · 决定网格 / 列表两种排版的展示框
  ▼
ThumbnailImage(item, order)             · @State image / failed；.task(id: item.id) 触发加载
  │  ① 同步查内存缓存 → 命中就立刻显示（不占闸门、不排队）
  ▼
ThumbnailStore.thumbnail(for:order:)    · 唯一的调度中心（单例）
  │  ② 读设置开关 / 负缓存冷却检查
  │  ③ 同一个文件只建一个 Job（多个格子等同一份结果）
  │  ④ 磁盘缓存命中 → 直接返回（不占闸门、不产生流量）
  │  ⑤ 需要读网络 → await displayLimiter.acquire(order:)   ← 顺序在这一步被强制
  │  ⑥ 图片：分块读满 → ImageIO 降采样到 480px
  │     视频：小文件镜像 / 大文件流式解码首帧
  │  ⑦ JPEG 0.72 落磁盘缓存 → 写内存缓存
  ▼
回到 ThumbnailImage：赋值 @State image，SwiftUI 重绘这一格
```

取消是**贯穿全程**的：格子划出屏幕 → `.task` 被取消 → `withTaskCancellationHandler` 把 `CancellationBox` 置位 →
正在进行的 SMB 传输在下一个数据块返回时抛 `CancellationError`，整条链路退出，且**不落盘、不记失败**。

## 2. 模块职责表

| 模块 | 职责 | 不该做的事 |
| --- | --- | --- |
| `BrowserView` | 提供稳定的**显示序号**（过滤后的顺序号，不是文件名顺序） | 不要在这里 sleep / 排队 |
| `MediaTile` | 决定**展示框**（网格 1:1.15 / 列表 56×56） | 不要在这里决定解码尺寸 |
| `ThumbnailImage` | 加载状态机（loading / image / failed）、内存缓存快查、`scaledToFit` 居中 | 不要在这里读写磁盘缓存 |
| `ThumbnailStore` | 缓存（内存 + 磁盘）、去重、失败冷却、**有序闸门**、限流上限 | 不要在这里做 UI 排版 |
| `OrderedLimiter` | 「一次一个 + 按序号放行」的通用闸门 | 不要在里面碰网络或图片 |
| `ImageDownsampler` | 把任意格式解到指定长边（ImageIO 优先，BMP/TIFF 走完整解码兜底） | 不要给 UI 层用原图 |

# 第一部分：按顺序一个一个加载

## 3.1 用户的原始反馈，以及为什么「并发 + 谁先完成谁先显示」不满足

原始现象（用户原话）：
> 「缩略图不是按顺序一个一的出现，后面的会先加载一个出来，再从第一个开始按顺序加载。」

这不是「加载慢」，而是**次序错了**。如果放任并发，出图顺序取决于：

1. **任务发起顺序** —— SwiftUI 的 `.task` 什么时候跑，取决于 `LazyVGrid` 什么时候创建单元格（懒加载，先出现的先创建，但滚动时会插队）；
2. **网络返回顺序** —— 同一时刻发 30 个 SMB 读请求，NAS 侧线程池、文件大小、是否命中系统缓存，都会让后面的先回来；
3. **解码耗时** —— 一张 40MB 的 BMP 和一张 200KB 的 JPEG，解码差两个数量级。

三者叠加，用户看到的就是「随机位置冒出一张，然后才开始正常」。

所以本项目的做法是：**把「显示」这件事收敛成一条单通道，且这个通道永远先服务序号小的格子。**

## 3.2 第一步：给每个格子一个稳定的显示序号 `order`

`BrowserView.swift:101-104`（网格）与 `:113`（列表）：

```swift
LazyVGrid(columns: gridColumns, alignment: .center, spacing: 16) {
    ForEach(Array(visibleItems.enumerated()), id: \.element.id) { index, item in
        cell(for: item, order: index)   // ← index 就是显示序号
    }
}
```

要点：

- `order` 是**当前列表里的下标**，也就是「从左到右、从上到下」的阅读顺序；
- 搜索过滤后 `visibleItems` 变了，`order` 会**重新连续编号**（不是原始目录序号），所以过滤后依然按新顺序出图；
- 列表模式（`List`）用同一套 `enumerated()`，序号就是行号；
- `order` 一路透传：`MediaTile(order:)` → `ThumbnailImage(order:)` → `ThumbnailStore.thumbnail(order:)` → `displayLimiter.acquire(order:)`；
- 只是「显示序号」，**不参与缓存 key**（key 用 `serverID|path|size|mtime`），所以同一个文件在网格和列表里共用同一份缓存，但各自带自己的序号去排队。

## 3.3 第二步：一道合并的闸门（图片 + 视频共用）

`ThumbnailStore.swift:62-66`：

```swift
/// 缩略图唯一的闸门：图片和视频共用，一次只跑一个、按格子序号放行。
/// 分成「图片 3 并发 + 视频 1 并发」两道闸门时是排不出全局顺序的
/// （视频可能比它前面几张图片先返回），所以合并成一道。
private let displayLimiter = OrderedLimiter(limit: 1, settleMilliseconds: 250)
```

历史教训（1.0.11 之前）：图片用 `AsyncLimiter(limit: 3)`、视频用 `AsyncLimiter(limit: 1)`。
结果第 3 个是视频、第 5 个是图片时，视频先跑、图片排队，出图顺序照样乱。
**只要存在两条队列，就不可能有全局顺序** —— 这是最容易被忽略的一点。

`limit: 1` 的含义：同一时刻只允许 **一个** 格子处在「读网络」阶段。
这不是性能妥协：瓶颈本来就落在「一次 SMB 读 8MB / 一次 1MB 顺序读」上，
并发 3 个只是把 NAS 打得更乱，整体完成时间并不会变短（甚至更长，因为 NAS 侧上下文切换和小文件抢占）。

## 3.4 第三步：`OrderedLimiter` —— 先聚集，再选拔

普通闸门的逻辑是「来一个放一个」，这会产生一个**只靠序号排序解决不了的抖动**：

> 40 个格子几乎同时发起请求，但谁先跑到 `acquire()` 是不确定的。
> 如果第一个到达的是第 12 格（它先读完了同步的磁盘缓存检查），闸门就先把第 12 格放行了，
> 于是出现「先冒出一张后面的，然后才从第一个开始」—— 正是用户反馈的第二种现象。

所以闸门在「从空闲转忙」的那一刻，**先睡一个聚集窗口**，让这一批格子把序号都登记进来，再挑最小的放行。

### 3.4.1 状态机的三个字段

```swift
private var running = 0            // 当前放行中（正在跑）的个数，limit=1 时只会是 0/1
private var waiters: [Waiter]      // 已登记、还没放行的请求（order + 到达流水号 seq + continuation）
private var pendingSettle = true   // 下一次放行前要不要先聚集
private var lastActivityNanos: UInt64?  // 上次放行/释放的时刻，用来判断「是不是新的一批」
```

```
                  acquire(order:) 到达
                          │
        ┌─────────────────┴─────────────────┐
        │ 空闲(running==0 且 waiters 为空)？ │
        └─────────────────┬─────────────────┘
             是           │            否（队列里已经有人）
        ┌─────────────────┴───────────────┐
        │ 距上次活动 ≥ 400ms ？            │  否 → 直接登记
        │  是 → pendingSettle = true      │
        │  否 → pendingSettle = false     │  （滚动时一张接一张来，不用再等）
        └─────────────────┬───────────────┘
                          ▼
                登记进 waiters + Task { pump() }
                          ▼
         pump: 若 pendingSettle → sleep 250ms（期间后来的格子继续登记）
                          ▼
              从 waiters 里挑 order 最小的 → resume() → running = 1
                          ▼
                    请求跑完 → release() → running = 0 → 再 pump()
```

### 3.4.2 `acquire`（`AsyncLimiter.swift:72-91`）

```swift
func acquire(order: Int) async {
    if running == 0, waiters.isEmpty {
        // 从空闲转忙：只有「隔了一段时间」才当成新一批，需要聚集；
        // 连续滚动时一张接一张地来，不额外等待
        let now = DispatchTime.now().uptimeNanoseconds
        if let last = lastActivityNanos {
            pendingSettle = now &- last >= burstGapNanos
        } else {
            pendingSettle = true
        }
    }

    sequence += 1
    let seq = sequence
    await withCheckedContinuation { continuation in
        waiters.append(Waiter(order: order, seq: seq, continuation: continuation))
        // 不能在 continuation 体内直接 await pump（会把「登记」卡住）
        Task { await self.pump() }
    }
}
```

三个容易写错的点：

1. **`Task { await self.pump() }` 而不是 `await self.pump()`**
   `withCheckedContinuation` 的闭包必须是同步的；而且如果在这里直接 `await pump()`，
   这个 actor 会在 `pump` 里挂起，导致**后面的格子登记不进来**（只能一个个来，聚集就失效了）。
   用 `Task` 把它推到下一轮 actor 调度，`waiters.append` 立刻生效，`pump` 睡醒时队列里已经是整批。

2. **`pendingSettle` 只在「从空闲转忙」时设置**
   一批里只有第一次需要等 250ms。之后闸门一直有活，`pump` 的循环里直接挑最小序号，不会再睡。

3. **`burstGapMilliseconds = 400` 的意义**
   用户往下滚动时，新格子是一张接一张出现的（间隔通常 < 400ms）。这种情况**不需要聚集**，
   否则每滚一格画面就卡 250ms 才出图。只有「停下来 / 进目录 / 切换排序」这种整批涌入，才值得等 250ms。
   这个判断用 `lastActivityNanos`（上一次 `release` 或放行的时刻）做差。

### 3.4.3 `pump`（`:99-126`）—— 挑最小的那个

```swift
private func pump() async {
    guard !pumping else { return }   // 同一时刻只允许一个 pump，避免重复放行
    pumping = true
    defer { pumping = false }

    while running < limit, !waiters.isEmpty {
        if pendingSettle {
            // 睡眠期间 actor 可重入，这一批格子会继续把序号登记进来
            try? await Task.sleep(nanoseconds: settleNanos)
            pendingSettle = false
        }
        guard !waiters.isEmpty else { break }

        var best = 0
        for index in 1..<waiters.count {          // 线性扫，waiters 通常 < 100，够用
            let candidate = waiters[index]
            let current = waiters[best]
            if candidate.order < current.order
                || (candidate.order == current.order && candidate.seq < current.seq) {
                best = index
            }
        }
        let waiter = waiters.remove(at: best)
        running += 1
        lastActivityNanos = DispatchTime.now().uptimeNanoseconds
        waiter.continuation.resume()
    }
}
```

- **`seq` 兜底**：`order` 理论上唯一（就是下标），但列表/网格切换、重复 cell 重建时可能撞号，
  用「到达流水号」做 tie-break，保证永不出现两个 waiter 互相比较相等而退化成 FIFO 抖动。
- **`pumping` 互斥**：`acquire` 和 `release` 都会 `Task { pump() }`，没有这个标记会出现
  「两个 pump 同时看到 `running == 0`，各放行一个」，`limit: 1` 直接失效。
- **`Task.sleep` 期间 actor 可重入**：这正是聚集能生效的原因 —— 睡着了，别的格子照样能 `acquire` 进来登记。
- **计时用 `DispatchTime.now().uptimeNanoseconds`**：纯整数比较，不涉及 `Clock.Instant` 的比较/求差，
  在 actor 里也不引入额外的 `Duration` 进位问题。休眠本身用 `Task.sleep(nanoseconds:)`。

## 3.5 只有「要读网络」的请求才排队

这是让「顺序」和「性能」不冲突的关键：闸门包住的只是**取图那一小段**。

`ThumbnailStore.produce`（`:182-229`）的执行顺序：

```swift
// ① 磁盘缓存命中：不产生任何网络流量  →  不碰闸门
if let data = try? Data(contentsOf: url), let cached = UIImage(data: data) { return cached }

// ② 需要读网络，才进闸门
await displayLimiter.acquire(order: order)
if cancel.isCancelled { await displayLimiter.release(); return nil }
image = item.kind == .image ? await imageThumbnail(...) : await videoThumbnail(...)
await displayLimiter.release()
```

再加上 `ThumbnailImage.load()`（`MediaTiles.swift:75-97`）开头还有一次**内存缓存同步快查**：

```swift
if let cached = ThumbnailStore.shared.cachedThumbnail(for: item, serverID: serverID) {
    apply(cached); return          // 命中就直接赋值，连 async 都不用等
}
```

于是：

| 场景 | 是否排队 | 表现 |
| --- | --- | --- |
| 首次进目录 | 全部要读网络 | 严格按序号一个一个出现 |
| 第二次进同一目录（有磁盘缓存） | 不排队，但每张要读一次本地文件 + 解码 | 很快全部出现，肉眼看到的是「唰」一下，无顺序问题 |
| 滚动回来（内存缓存命中） | 不排队 | 立即显示 |
| 同一文件被两个视图同时请求 | **共用同一个 Job** | 只读一次网络，两个格子同时亮 |

> 有人会问：磁盘缓存命中不排队，会不会又乱序？
> 不会。磁盘命中的前提是「这张图之前已经加载过」，用户已经见过它了；
> 而且这些命中都是本地顺序执行、耗时 < 10ms，视觉上是一起出现的，不构成「后面的先冒出来」。

## 3.6 取消、去重与失败冷却（不打断顺序）

### 3.6.1 去重：同一文件只跑一次

`makeJob`（`:130-150`）用 `jobs[key]` 存正在跑的任务，多个格子（比如网格和列表同时存在、
或者同一张图被两个视图引用）会 `waiters += 1` 共享同一个 `Task`。

### 3.6.2 取消：没人等就立刻掐断

```swift
let result = await withTaskCancellationHandler {
    await job.task.value
} onCancel: {
    // 视图被划走 / 页面退出：没有人再等这张图了，直接掐断传输
    if waiter.finishOnce() { ThumbnailStore.shared.detach(key: key, job: job) }
}
```

`detach`（`:152-163`）做引用计数减一，归零时 `job.box.cancel()` 置位取消标记；
`SMBConnection.read` 在下一个数据块返回时抛 `CancellationError`，`produce` 里立刻 `return nil`。

**注意 `produce` 里那句 `if cancel.isCancelled { await displayLimiter.release(); return nil }`**：
如果请求在闸门里排队时被取消，`acquire` 仍然会正常返回（continuation 不能中途丢弃），
所以**必须在 acquire 之后补一次检查并主动 release**，否则 `limit: 1` 的闸门会被一个死请求永久占住 —— 表现就是「缩略图再也不加载了」。

### 3.6.3 被取消的不算失败

```swift
// 被取消就不落盘、也不记失败，下次出现时还能重来
if cancel.isCancelled { return nil }
```

否则「快速滚动经过的图」会全部进失败列表，回来时反而被负缓存挡住。

### 3.6.4 失败冷却 180 秒

`markFailure` / `isCoolingDown`（`:165-178`）：真失败（读不满、解码失败、超出上限）时记时间戳，
180 秒内同一个 key 直接返回 nil，避免「划回去就重试」把 NAS 打满。
用户在设置页手动「重新加载失败的」时调 `resetFailures()` 清空。

## 3.7 参数为什么是这几个数

| 参数 | 值 | 调大的后果 | 调小的后果 |
| --- | --- | --- | --- |
| `limit` | **1** | 2~3：顺序仍对（闸门会按序号放行），但可能同时有两张在网络上，第二张先回来也要等第一张 release 才显示——顺序不乱，只是多了并发噪声；NAS 压力上升 | 0 非法（内部按 1 处理） |
| `settleMilliseconds` | **250** | 400~500：进目录后第一张图明显「卡一下」才出现 | 50~100：格子登记不全就开始放行，仍会偶尔乱序（尤其慢机型 / 冷启动） |
| `burstGapMilliseconds` | **400** | 800+：滚动时每张都触发聚集，滑动中一格一格停顿 | 100~200：滚动时也走聚集，滚动观感变卡 |

经验公式：`settle ≈ 两帧 × 一批格子的创建耗时`。这一批格子（约 12~30 个）在 iPhone 上登记完大约 120~200ms，
250ms 留了 50ms 余量；`burstGap` 取 `settle` 的 1.6 倍，保证「一批之内只等一次」。

## 3.8 试过但不采用的做法

| 做法 | 为什么不行 |
| --- | --- |
| `for item in items { await load(item) }` 顺序串行 | 界面首页要等全部跑完才有图；滚动时无法插队；取消粒度太粗 |
| `withTaskGroup` + 全部 `await` | 任务组内部仍然是并发，出图顺序 = 完成顺序；而且取消一个成员会把整组带崩 |
| 在 `ThumbnailImage` 里 `.task { try await Task.sleep(index * 80ms); load() }` | **依赖 SwiftUI 什么时候创建这个 cell**，懒加载下第 20 格可能比第 3 格先创建，延迟反而错位；滚动时延迟叠加，越来越慢 |
| 用 `AsyncLimiter(limit: 1)`（FIFO） | 只保证「一个一个」，不保证「按序号」：谁先到谁先跑，仍是先冒出后面的（1.0.10 就是这样） |
| 等全部下载完再一次性显示 | 用户要的是「一个一个出现」的**过程感**，不是一次性；而且首屏等待太久 |

## 3.9 自测顺序是否生效

1. 进一个**从未进过**的目录（保证无缓存）：缩略图应从左上第一个开始，一格一格往右下推进；
2. 打开飞行模式再关掉 / 换个延迟高的网络（或用限速），顺序是否正确最容易看出来；
3. 反复上下滚动：滚出屏幕的格子会被取消，滚回来时**已加载的立即出现**，这是预期行为，不算乱序；
4. 搜索过滤后：序号重排，从过滤结果的第一个开始；
5. 网格 ⇄ 列表切换：各自按自己的序号走，共用缓存。

# 第二部分：竖屏 / 横屏按比例显示

## 4.1 三层尺寸，各管一件事

```
① 解码尺寸（像素）        ② 展示框（点，布局）           ③ 图片内容（点，绘制）
ImageIO 缩放到长边 480  →  TileAspect.box = 0.87         →  .scaledToFit()
「够清晰且不浪费内存」      「格子大小统一，行高不抖」        「不变形、不裁切，框内居中」
```

这三层互不干扰：改解码尺寸不影响布局，改展示框不影响清晰度。**不要合并**（1.0.8 就是把②交给①的真实比例，导致行高乱跳）。

## 4.2 为什么是「固定展示框」而不是「按图片真实比例撑格子」

被否掉的方案（1.0.8）：
每张图算出自己的宽高比，用 `.aspectRatio(realRatio, contentMode: .fit)` 撑格子。
后果：

- 一张 9:16 的竖屏图，把**整行**的行高从「列宽 × 1.15」拉到「列宽 × 1.78」；
- 同一行里混着 16:9 横屏图时，横屏图的格子被撑高而图片只占中间一条，看着像「在格子里居中」；
- 行高随内容变化 → `LazyVGrid` 每次重算布局，滚动时明显掉帧，且会出现「跳一行」。

现在的方案：
**所有格子（图片、视频、文件夹、其它文件）共用同一个框**，宽高比固定 `0.87`（宽 : 高 = 1 : 1.15）。
于是：

- 每列宽度一致 → 每行高度一致 → 整个网格是规整的矩阵；
- 横屏图在框里上下留白，竖屏图左右留白，**留白就是页面底色**，不是灰块；
- 图片 `.scaledToFit()` 完整显示，永远不裁切。

### 4.2.1 `0.87` 是怎么定出来的

```
屏宽 390pt
 - 左右页面内边距 12 × 2  = 24
 - 列间距 12 × 2          = 24
 = 342 / 3 列 ≈ 114pt（每格宽）

框高 = 114 / 0.87 ≈ 131pt
```

- 正方形（1.0）时，竖屏 3:4 的照片在框里左右留白偏多，视觉上「图很小、格子很空」；
- 取 1 : 1.15 后，竖屏照片（3:4）左右留白约 20%，横屏照片（4:3）上下留白约 25%，两者观感接近；
- 再高（比如 1:1.4）横屏图的留白就太多了，像「一条横线挂在格子中间」。

`MediaTiles.swift:7-10`：

```swift
enum TileAspect {
    /// 展示框的「宽度 / 高度」（0.87 ≈ 宽:高 = 1 : 1.15）
    static let box: CGFloat = 0.87
}
```

## 4.3 图片在框内的定位：`fit` + 居中 + 只裁图片自己

`MediaTiles.swift:29-56`：

```swift
ZStack {
    if let image {
        Image(uiImage: image)
            .resizable()
            .scaledToFit()                                  // ← 保持自身宽高比，完整显示
            .overlay(alignment: .bottomLeading) {
                if showPlayBadge, item.kind == .video { playBadge }
            }
            .clipShape(RoundedRectangle(cornerRadius: cornerRadius, style: .continuous))
    } else {
        RoundedRectangle(cornerRadius: cornerRadius, style: .continuous)
            .fill(Color(uiColor: .secondarySystemFill))      // ← 只在没图时才有底板
            .overlay { failed ? 占位图标 : ProgressView() }
    }
}
// 撑满展示框并居中：横屏图上下留白、竖屏图左右留白，都是均匀的
.frame(maxWidth: .infinity, maxHeight: .infinity, alignment: .center)
.contentShape(Rectangle())
```

三个细节，缺一不可：

1. **`.scaledToFit()`**：等比缩放到「刚好装进框」，**不裁切**。
   当年用 `.scaledToFill()` + `clipShape` 的版本会把横屏图裁掉左右、竖屏图裁掉上下（1.0.6 的 bug）。
2. **`.frame(..., alignment: .center)`**：`scaledToFit` 产生的空白默认按居中排，
   但显式写 `.center` 才能抵消外层 `GridItem(alignment: .top)` 的影响 —— 1.0.9 的「横屏图顶着上边」就是这里被 `.top` 带走了。
3. **圆角裁在图片上，不是裁在格子上**：`clipShape` 挂在 `Image` 上，
   于是竖屏图的圆角贴着图片自己的左右边，两侧的留白是干净底色；
   如果反过来把圆角画在整个框上，就会变成一个「灰色圆角底板 + 图片浮在上面」的观感 —— 也就是 1.0.9 那个「有灰边」的问题。

### 4.3.1 布局链条完整走一遍

```swift
// MediaTiles.swift:175-188（网格）
VStack(spacing: 6) {
    ThumbnailImage(...)
        .aspectRatio(TileAspect.box, contentMode: .fit)   // ① 框：宽度由列决定，高度 = 宽 / 0.87
    FileNameLabel(name: item.name)                        // ② 固定两行高
    TileCaption(size:date:)                               // ③ 两行小字
}
```

- `GridItem(.flexible(), spacing: 12, alignment: .top)`：列宽均分，行内顶部对齐；
- `.aspectRatio(0.87, contentMode: .fit)`：这里 `aspectRatio` 是**比例约束**（不是内容填充模式），
  在列宽被确定后，把高度锁成 `width / 0.87`；
- `FileNameLabel` 内部 `.frame(minHeight: 32, alignment: .top)`：**固定两行高度**，
  所以短文件名（1 行）和长文件名（2 行）不会让下面的大小/日期错位 —— 这是「同一行三列底端也齐」的关键；
- `TileCaption` 两行（大小 / 日期），`.multilineTextAlignment(.center)`。

## 4.4 解码尺寸 480px 的推导

`ThumbnailStore.swift:14-15`：

```swift
/// 统一缩略图长边像素（网格最宽 160pt × 3 倍屏 = 480）
private static let pixelSize = 480
```

- 展示框宽 114pt @3x = 342px，高 131pt @3x ≈ 393px；
- 解码长边取 480px：横屏图 480×360（覆盖 342px 宽 ✓），竖屏图 360×480（覆盖 393px 高 ✓）；
- 取「长边」而不是「固定宽高」，是为了**任意方向都等比缩放到刚好够用**，不裁切、不变形；
- 不做 2 倍/3 倍两套：图像最终都会被 fit 进框，480 在 3x 屏上仍有 ~1.2 倍冗余，肉眼无差别，
  而内存从「480² × 4B ≈ 0.9MB」涨到「960² × 4B ≈ 3.7MB」不划算（600 张就是 2.2GB）。

内存缓存上限也是按这个算的：`countLimit = 600`、`totalCostLimit = 64MB`，cost 用 `bytesPerRow × height`。

## 4.5 方向（EXIF）必须转正，否则竖拍照片会「躺着」

`ImageDownsampler.thumbnail`（`:50-61`）：

```swift
let options: [CFString: Any] = [
    kCGImageSourceCreateThumbnailFromImageAlways: true,
    kCGImageSourceCreateThumbnailWithTransform: true,   // ← 按 EXIF 方向旋转
    kCGImageSourceShouldCacheImmediately: true,
    kCGImageSourceThumbnailMaxPixelSize: maxPixel
]
guard let cgImage = CGImageSourceCreateThumbnailAtIndex(source, 0, options as CFDictionary) else { return nil }
```

- `CreateThumbnailWithTransform: true`：手机竖拍的照片（EXIF Orientation = 6/8）会被**转正**成竖图，
  否则一张竖拍人像在网格里是横躺的，而且宽高比看起来也不对；
- `kCGImageSourceShouldCache: false`（source 级）：避免 ImageIO 在内存里留一份全尺寸解码缓存；
- **两条路兜底**：`CGImageSourceCreateThumbnailAtIndex` 失败的格式（BMP / TIFF 常见）退到
  「完整解码 + `UIGraphicsImageRenderer` 按长边等比缩放」（`:64-92`），且 `format.opaque = true` +
  `blendMode = .copy` —— 32 位 BMP 的 alpha 常常全为 0，带 alpha 画出来会变成全透明（看起来全黑）。

## 4.6 列表模式的框

列表里缩略图是 `56 × 56` 的方框（`MediaTiles.swift:190-201`），同样是 `scaledToFit` + 居中：

```swift
ThumbnailImage(..., cornerRadius: 6, order: order, showPlayBadge: false)
    .frame(width: 56, height: 56)
```

- 正方形小框 + 完整显示，横图上下留白、竖图左右留白，行高固定 56+16 不变；
- `showPlayBadge: false`：列表行右侧已经有 `play.rectangle.fill` 小图标，角标不重复画。

## 4.7 这一块踩过的坑（按时间）

| 版本 | 现象 | 根因 | 现在 |
| --- | --- | --- | --- |
| 1.0.6 | 横图被裁左右、竖图被裁上下 | `scaledToFill()` + `clipShape` | `.scaledToFit()` |
| 1.0.8 | 竖屏缩略图巨大、行高乱跳 | 用真实宽高比撑格子 | 固定 `TileAspect.box` |
| 1.0.9 | 格子有灰边、横屏图贴顶 | 灰底当整格底板 + `frame(alignment: .top)` | 有图只画图、`.center` |
| 1.0.9 | `LazyVGrid(alignment: .top)` 编译不过 | 参数类型是 `HorizontalAlignment`，`.top` 是 `VerticalAlignment` | 行内对齐交给 `GridItem(alignment: .top)` |
| 1.0.10 | 短文件名的格子，下面的大小/日期被顶上去 | 文件名行高随内容变化 | `FileNameLabel` 固定 `minHeight: 32` |

## 4.8 想要「不同比例不同框」怎么办

如果以后要改成「视频 16:9、照片 3:4」的混合布局（很多相册 App 这么干），正确做法是：

1. **框的比例由类型决定，不由具体图片决定**（视频固定 16:9、照片固定 3:4），行高仍然可控；
2. 用 `GridItem(.adaptive(minimum:))` 或者干脆放弃 `LazyVGrid`，改用两行瀑布流；
3. 图片仍然 `scaledToFit`；
4. **不要回到「按每张图真实比例」** —— 那是行高失控的起点。

| 目标 | iOS（本项目） | Android | Flutter | Web |
| --- | --- | --- | --- | --- |
| 有序出图 | 自写 `OrderedLimiter`（聚集窗口 + 最小序号） | `CoroutineDispatcher` 限 1 并发 + `PriorityQueue`（按 adapter position） | 自写 `AsyncQueue` + `StreamController`，或 `PriorityQueue` + 单 worker | 单个 `fetch` worker + 最小 index 优先（`Promise` 队列） |

# 8. 排障：出不来时看哪里

1. **设置 → 缩略图 → 加载失败记录**：每次失败都会写一条（文件名 + 原因），失败原因都是人话：
   - `图片 69MB 超出上限 160MB`
   - `图片只读到 12582912/72430592 字节`（读不满 = 会被判定为截断，宁可不显示也不糊半截图）
   - `解码失败（bmp 69MB）`
2. **顺序不对**：先确认是不是「磁盘缓存命中」造成的错觉（第二次进目录是瞬间全部出现，属正常）。
   真乱序时检查三点：`displayLimiter` 是否被拆成了两道、`order` 是否仍来自 `enumerated()`、
   `settleMilliseconds` 是否被改小于 150。
3. **只出一张就不动了**：99% 是闸门泄漏 —— 某个请求在 `acquire` 之后没走到 `release`
   （`produce` 里所有提前 `return` 的分支都必须先 `release`）。
4. **格子变形/拉伸**：检查是不是有人给 `Image` 加了 `.resizable()` 却漏了 `.scaledToFit()`
   （默认是 `.fill`，会拉伸变形）。
