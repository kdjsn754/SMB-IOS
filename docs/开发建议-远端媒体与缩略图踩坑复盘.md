# 远端媒体客户端开发建议
## —— 从 SMBViewer 1.0.0 → 1.0.14 的 14 个坑里提炼

> 适用对象：任何要「从远端（SMB / WebDAV / 网盘 / HTTP）读媒体、在列表里显示缩略图、点开能播」的客户端。
> iOS 具体 API 在文末第 7 节给了 Android / Flutter / Web 的对照，思路是通用的。

---

## 0. 一句话总结

远端媒体客户端里 90% 的「玄学 bug」都不是玄学，而是三件事撞在一起：

1. **把截断的文件当成完整文件**（只读了文件头，却让解码器按完整文件的索引去解析）；
2. **把「能播放」当成「能抽帧」**（播放器是顺序预读，取帧是随机索引）；
3. **把「谁先跑到」当成「谁先该显示」**（并发闸门按到达顺序放行，而到达顺序由 UI 框架决定）。

## 2. 四个值得单独讲的根因

### 2.1 「截断的文件不是文件」

**现象**：522 MB 的 MP4，封面永远抽不出来；改成「只读文件头 12/24/40/48 MB 拼一个迷你文件」后依然失败。
**我最初的误判**：以为「首帧没被覆盖到」，于是一路加大文件头长度（12 → 24 → 40 → 48 MB），全是白费流量。

**取证**：把文件结构打进诊断，得到一行
`ftyp@0 free@32 mdat@40(522MB) moov@547662742(412KB)`
—— 文件 522 MB，`moov` 在**文件尾部**，`mdat` 从偏移 40 开始。

**真因**：`moov` 里的样本表（`stco`/`stsz`）记的是**相对原始文件的绝对偏移**。我把 `mdat` 从 522 MB 砍到 48 MB 之后，所有偏移全部越界，AVFoundation 一加载就判定「这个电影文件损坏」→ `-11821`（`AVError.decodeFailed`）。**和首帧在不在镜像里完全无关**。

**结论 / 可复用规律**：
> 任何「只读一部分」的优化，必须先证明**这个格式允许在这个位置截断**，否则就是在制造损坏文件。

- 允许截断的位置：`fMP4` 的 fragment 边界（`moof` + 完整 `mdat`）、`BMP` 的定长扫描行、单独的 JPEG 扫描段；
- 不允许的位置：`mdat` 中间、`moov` 中间、ZIP 的中央目录之后；
- 同一个坑在**断点续传 / 断线重连**里也常见：拿到半截文件就当完整文件去解析，报错信息通常只有一句「格式不支持」。

**修法**：按文件大小分流 —— ≤64 MB 整份读进来做镜像（等于不截断），大的不做镜像，走流式顺序解码。

---

### 2.2 「能播放 ≠ 能抽帧」

**现象**：抽帧报 `-11821`，可同一个文件在 App 里点开播放完全正常。用户这句话价值极高：**它排除了一整类可能**。

**逐层排除**（这一步比改代码重要）：
1. 编码不认识？→ 诊断里 fourcc 是 `avc1`，且能播 → ❌ 排除
2. `moov` 找不到？→ 报错不是这条 → ❌ 排除
3. 数据没读到？→ 镜像和流式两条路都报同一个 `decodeFailed` → 说明「拿到了数据但解不出来」→ 问题在**取帧方式**，不在数据量

**真因**：`AVAssetReader` 要按 `moov` 的样本表**逐个区间随机取数**，`AVAssetImageGenerator` 要**按时间 seek**。两者都要求「我要的那段字节现在就有」。而自定义 `AVAssetResourceLoaderDelegate` 只保证「你要什么我给什么」，不保证「你要的区间正是解码器认为必须的」——时机和顺序都不由我们控制。像素级顺序预读的 `AVPlayer` 反而没事。

**修法**：远端资产用**播放器管线**取帧 —— `AVPlayer` + `AVPlayerItemVideoOutput`，和 App 里播放走完全同一条路：

```swift
let item = AVPlayerItem(asset: asset)
let output = AVPlayerItemVideoOutput(pixelBufferAttributes: [
    kCVPixelBufferPixelFormatTypeKey as String: NSNumber(value: kCVPixelFormatType_32BGRA)
])
item.add(output)
let player = AVPlayer(playerItem: item)
player.isMuted = true
player.automaticallyWaitsToMinimizeStalling = false
player.play()

// 80 ms 轮询，最多 12 秒；拿到第一帧立刻停
if output.hasNewPixelBuffer(forItemTime: item.currentTime()),
   let buffer = output.copyPixelBuffer(forItemTime: item.currentTime(), itemTimeForDisplay: nil) {
    return makeImage(from: buffer, transform: preferredTransform)
}
```

**代价要认**：这条路要「真的播一下」（约 0.3～1 秒），所以
- 一定**放在低并发队列里**（我们是缩略图闸门内一次一个）；
- 一定**静音 + 不接管音频会话**（`isMuted = true`，别去 activate AVAudioSession）；
- 一定**有超时和取消**，否则一个坏文件会阻塞整屏；
- 抓完立刻 `player.pause()` + `replaceCurrentItem(with: nil)`，别让播放器在后台偷偷预读。

**同类产品的普遍做法**：视频编辑 / 相册 / NAS 客户端给远端视频生成封面时，普遍走「播放器 + 视频输出」或用自建的分片读取器，而不是直接把远端 URL 丢给 `AVAssetImageGenerator` —— 后者对「索引齐全 + 随机可读」的要求太硬。这也解释了为什么很多 App 的封面在本地文件上没问题、接上 NAS/网盘就大面积灰块。

### 2.3 并发不是排队的同义词

**现象演进（同一问题修了三次）**：

| 版本 | 做法 | 为什么还错 |
|---|---|---|
| 1.0.7 | 图片 3 并发 + 视频 1 并发，两道独立闸门 | 跨类型没有全局顺序，视频可能比它前面几张图先返回 |
| 1.0.11 | 合并成一道闸门，排队时优先放行**序号最小**的 | `acquire` 里「还有空位就直接放行」—— 开头几个名额谁先抢到纯看任务调度 |
| 1.0.14 | 空闲转忙时先**聚集 250 ms**，等这批格子把序号登记完，再挑最小的放行 | ✅ |

**为什么会「先冒出一张靠后的」**：网格里几十个格子的 `.task` 几乎同时发起，但**谁先跑到闸门**取决于 UI 框架起任务的顺序 + 每个格子读磁盘缓存花的毫秒数。到达顺序和显示顺序本来就是两件事。

**为什么不用「等齐所有格子再开始」**：不可见格子永远不会发请求，等它会死锁。正确做法是**只等一小段时间就问「现在最小的序号是几」**，让先到的、后到的都能在同一次选拔里比较。

**可复用规律**：
> 只要 UI 层是「并发发起 + 按序号展示」，闸门就必须**按业务序号选拔**，并且要有**聚集窗口**吸收抖动。

这条在 Android 上同样是坑：`Glide`/`Coil` 的请求默认先到先得，滚动时缩略图会「跳着出现」，需要显式给请求优先级 / 序号；我们自己写线程池时更是重灾区。

### 2.4 静默失败是最贵的 bug

**现象**：69 MB 的 `.bmp` 全部不出缩略图，设置页里**一条诊断都没有**。用户只能反馈「有的加载不出来」，我完全无法定位。

**真因**：`guard size <= 64MB else { return nil }` —— 拦截了，但没留痕。

**规范（强烈建议写进团队 review 清单）**：
> 每一个 `return nil` 之前，必须能回答「谁、多大、走到哪一步、什么错」。答不上来就先写诊断再优化。

诊断本身也应该当**产品功能**做：
- **一行显示得完**（设置页一行显示不下会被省略号截掉，长信息要拆成多条短句）；
- **带结构摘要**（文件大小 + 盒子/轨道布局 + 编码 + 首帧位置），一眼能判断「是不是结构问题」；
- **可清除**（否则新记录被旧记录顶掉，用户以为没更新）；
- **有上限**（保留最近 8 条足够，别无限增长）。

## 3. 可以直接搬走的 8 条工程准则

1. **先取证，再改代码。** 每一次「我猜是 X」都要变成「诊断里出现了 X 的证据」。本项目 3 次误判全部是因为跳过取证直接改（加大文件头 / 换容器 / 加超时）。
2. **分层降级，每层只做自己能保证的事。** 内存 → 磁盘 → 远端；远端内部再分「安全路径（格式允许）」和「不安全路径（需要整份数据）」。
3. **一切截断都要有格式依据**（见 2.1）。
4. **并发闸门按业务序号选拔，不按到达顺序**（见 2.3）。
5. **失败必须留痕**（见 2.4）。
6. **缓存三件套**：正缓存（NSCache + 磁盘 LRU）、负缓存（失败 TTL 3 分钟，避免划回去就打满 NAS）、失效键（`服务器 + 路径 + 大小 + mtime`，服务器上文件一改自动失效）。
7. **取消要贯穿全链路**：视图划走 → `CancellationBox.cancel()` → 阻塞中的 SMB 读立刻中断 → 已读字节不再写缓存。没有取消的缩略图系统在快速滑动时会把自己拖死。
8. **一次只改一个可验证的假设**，改完立刻跑 CI + 产物自检（见第 5 节）。

## 4. 缩略图子系统推荐架构

```
视图层   ThumbnailImage       只负责「要一张图」+ 显示，不关心来源
  │
调度层   OrderedLimiter       按格子序号放行，一次 N 个（本项目 N=1）
  │
取数层   SMBConnection        区间读 + 字节预算(ByteBudget) + 取消(CancellationBox)
  │        ├─ 图片：整份读满 / 大图落临时文件
  │        └─ 视频：≤64MB 本地镜像 ｜ >64MB smbstream:// 流式
  │
解码层   ImageDownsampler     长边 480 下采样，内存占用可控
         VideoFrameDecoder    播放器管线 → 顺序解码 → 按时间取帧（三级降级）
  │
缓存层   NSCache + Caches/Thumbnails   (200MB 起，按写入时间 LRU)
  │
诊断层   ThumbnailDiagnostics 环形 8 条，设置页可见、可清除
```

三个容易漏的点：

- **「加载中」和「失败」必须是两个状态。** 一直转圈是最糟的体验 —— 失败要明确退化成占位图标。
- **一次失败不要立刻重试。** 负缓存 180 秒，否则用户来回滑两次就能把 NAS 打满。
- **同一文件只生成一份缩略图**，网格和列表共用同一份 480px，别按视图各生成一套。

## 5. 未签名 IPA + 用户自签安装的自检清单

CI 出包、用户自己重签，等于**你无法在开发机上复现用户的运行环境**，所以产物要在 CI 里做结构断言：

| 检查项 | 为什么 | 怎么查 |
|---|---|---|
| `Info.plist` 的版本号 = 预期 | 用户装了才知道有没有生效 | 解压 ipa 读 `Payload/*.app/Info.plist` |
| **Payload 里不能有 `Frameworks/` 目录** | 自签工具常漏签内嵌 dylib → 启动即闪退 | `find Payload -name Frameworks` |
| 可执行文件是 arm64 | 别把模拟器架构打进包 | Mach-O magic `cffaedfe` + cputype |
| `.app` 里只有一个可执行文件 | 多出来的通常是没被签的扩展/dylib | 列 `Payload/*.app` 一级条目 |
| CI 里断言 `otool -L` 只剩系统库 | 静态链接的兜底 | `otool -L` grep 非 `/usr/lib`、`/System` |

配套的工程约定：`project.yml`（XcodeGen）是唯一工程定义、**不提交 `pbxproj`**；换行统一 LF；构建脚本保留可执行位。

## 6. 迁移到其他技术栈的对照

| 本项目（iOS） | Android | Flutter / Web | 注意点 |
|---|---|---|---|
| `AVAssetImageGenerator` 抽帧 | `MediaMetadataRetriever.setDataSource(url)` | `<video>` + canvas | 都对「远端 + 分片」不友好；通常先把**首段或整份**落到本地再抽 |
| `AVAssetReader` 顺序解码 | `MediaExtractor` + `MediaCodec` | WebCodecs | 需要自己处理样本表，随机访问要求更高 |
| `AVPlayer` + `AVPlayerItemVideoOutput` | `ExoPlayer` + `TextureView` 截帧 | `<video>` 播一帧后 `drawImage` | 通用解：**播放器截帧**，本地和远端都能用 |
| `ImageIO` 下采样 | `BitmapFactory` + `inJustDecodeBounds`/`inSampleSize` | `createImageBitmap` + resize | 关键是**先读尺寸再按需解码**，别整张解进来 |
| 自定义 `AVAssetResourceLoader` | OkHttp `Interceptor` / `DataSource` | `Range` 请求 + `Service Worker` | 都要实现：`Content-Length`、`Accept-Ranges`、精确区间返回 |
| 有序闸门 | 自己的 `ThreadPoolExecutor` + 优先级队列 | `p-limit` + 请求序号 | 别指望库默认给你顺序 |
| 诊断面板 | 内置 Debug 页面 | localStorage 环形日志 | 线上也保留，用户能截图给你 |

## 7. 给本项目的下一步建议（按性价比排序）

1. **BMP 行偏移跳读**：BMP 是定长扫描行 + 头部记录高度，可以只读「需要的几行」再拼成小图，一屏十几张 600 MB 的流量能降到 1/10 以下。前提是先验证「这个 BMP 变体确实是未压缩 24/32 位」。
2. **视频封面记下「抓到的是第几秒」**，以后做拖动进度条预览（trickplay）可以直接复用这套取帧链路。
3. **缩略图并发自适应**：目前固定 1 个（保证顺序）。可以按 RTT 自适应到 2，代价是极端情况下会差 1 个位置——需要用户明确「顺序优先」还是「速度优先」。
4. **真机回归清单**（本项目至今没有系统性回归）：
   - 500+ 文件的目录快速滑动，看内存峰值和取消是否生效；
   - 断网 / 切 Wi-Fi 重启后重进目录，看负缓存与重连；
   - 同名不同大小文件（改过的文件）是否重新生成缩略图；
   - MKV/AVI 是否明确显示「不支持」而不是一直转圈。

## 8. 最后

这套系统的复杂度不在「显示一张缩略图」，而在**远端的不确定性 × 平台 API 的隐含前提 × 用户的直觉期待**三者之间的缝隙。每一次「这不合理」的用户反馈，几乎都对应着一个我们没写进文档的隐含假设。

排查公式，可以直接贴在显示器上：

> **用户说「正常」的那个功能，是排除法的起点；**
> **用户说「不行」的那个动作，是定位的终点；**
> **中间那段，全靠诊断信息填。**
